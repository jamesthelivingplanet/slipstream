## Findings

### 1. `runLogger.server()` races its own rotation — log lines are misrouted and the cap is not enforced

`electron/services/runLogger.ts:122-142`

`server()` appends with **async** fire-and-forget `fs.appendFile`, but tracks
size in a **synchronous** counter and rotates with a **synchronous**
`fs.renameSync`. Appends still in flight when the rename fires resolve their
path *after* rotation, so they land in the fresh `server.log` instead of the
rotated `server.log.1`.

Consequences: `MAX_SERVER_LOG_BYTES` is not actually enforced (the rotated file
is arbitrarily smaller than the cap), and process-level log lines — the ones
that "survive restarts", including `uncaughtException` — land in a different
file than their neighbours, silently reordering forensic output.

**Reproduction.** `electron/services/runLogger.test.ts:160` fails under the full
suite's I/O load and passes in isolation:

```
FAIL electron/services/runLogger.test.ts > rotates server.log to server.log.1 once writes cross the cap
AssertionError: expected 7340263 to be greater than 9437184
```

7340263 is exactly 7 MiB — two of the nine ~1 MiB lines that should have been in
the rotated file were still in flight and landed post-rename. Isolated runs pass
3/3, so this is a genuine load-dependent race, not test flake, and the failing
gate is currently masked by looking like flakiness.

Fix direction: serialize writes behind a single append queue (or use a
persistent `fs.WriteStream` and rotate on its `drain`), so rotation cannot
interleave with an outstanding append.

### 2. `cleanupSession` cancels a queued session before checking ownership

`electron/core/rpcHandlers/sessions.ts:154-162`

```ts
deps.scheduler?.cancel(id)          // ← acts on any id
const persisted = ownedSession(id)  // ← ownership checked only after
if (!persisted) return { removed: false, reason: 'session not found' }
```

The scheduler cancellation is unconditional. A caller holding a valid device
token for owner *B* can cancel owner *A*'s queued session by id: the RPC
correctly returns `session not found` (no existence leak), but the queued run
has already been dropped from the scheduler. Cross-owner denial of service with
an honest-looking error.

This is precisely the invariant CLAUDE.md flags — *"Don't add a read of a
`sessions`/`repos` row without scoping it by owner"* — and every sibling handler
(`killSession`, `detachSession`, `takeWrite`, `sessionMerged`) gets the ordering
right. Moving the `ownedSession(id)` check above the `cancel` call is sufficient;
the comment explaining why cancel-comes-first is about racing the *drain*, which
an ownership check ahead of it does not affect.

Impact today is bounded — the static `SLIPSTREAM_TOKEN` resolves every caller to
`local`, so this needs the FLO-143 per-device token path to be exploitable — but
it is a live gap in the seam the multi-user tier is built on.

### 3. Electron 33.4.11 ships with four high-severity advisories, one of them on a surface this app uses

`package.json` pins `electron@^33.2.1`; resolved 33.4.11. Electron is a
devDependency but *is* the shipped desktop runtime, so these are user-facing.

| Advisory | Patched in |
| --- | --- |
| Renderer command-line switch injection (GHSA-9wfr-w7mm-pc7f) | ≥38.8.6 |
| Use-after-free in WebContents fullscreen (GHSA-8337-3p73-46f4) | ≥38.8.6 |
| Use-after-free in PowerMonitor on Windows (GHSA-jjp3-mq3x-295m) | ≥38.8.6 |
| Use-after-free in offscreen child window (GHSA-532v-xpq5-8h95) | ≥39.8.1 |

The command-line-switch injection one deserves attention specifically because
`electron/main.ts:46` passes secrets through exactly that channel —
`additionalArguments: [daemonArg, '--slipstream-app-url=' + appUrl]`, where
`daemonArg` carries the daemon bearer token (CLAUDE.md's `--slipstream-daemon=`
gotcha).

To be clear about what was and wasn't verified: I confirmed the vulnerable
version is what resolves, and that the app uses the named surface. I did **not**
demonstrate an exploit, and the advisory may well not be reachable given
`sandbox: true`. Treat this as upgrade-priority evidence, not a proven hole.

Mitigating context — window hardening is otherwise solid: `sandbox: true` on both
windows, CJS preload, `setWindowOpenHandler` plus `will-navigate`/`will-redirect`
origin guards (`electron/shared/navigationGuard.ts`).

Upgrading 33 → 39 is a major-version jump that will require a native ABI rebuild
of `better-sqlite3`/`node-pty` (see docs/NATIVE-MODULES.md), so it wants its own
ticket rather than a drive-by bump.

### 4. `package-lock.json` is vestigial *and* stale — it makes `npm audit` report a false clean

`package-lock.json` (350 KB) is tracked alongside `pnpm-lock.yaml`, but nothing
installs from it: `.gitlab-ci.yml` uses `pnpm install --frozen-lockfile`
throughout, and the only script that touches it is `scripts/release.sh:115-127`,
which bumps its embedded **version field** and commits it.

Because only the version field is maintained, its dependency graph has drifted.
Its root `dependencies` block is:

```
@xterm/*, better-sqlite3, node-pty, opencode-ai, web-push, ws
```

Missing versus `package.json`: **`dompurify`, `marked`, `qrcode`** (runtime
dependencies) and `@types/qrcode`.

The sharp edge: `npm audit --omit=dev` against this file reports
**"found 0 vulnerabilities"** — a clean bill of health for a runtime tree that
does not include the markdown parser and the XSS sanitizer, i.e. the two
security-relevant runtime packages. `pnpm audit --prod` (which reads the real
lockfile) independently also reports zero, so the *conclusion* happens to hold
today; the problem is that the npm-based check cannot be relied on to keep
holding.

Recommendation: delete `package-lock.json` and drop it from `release.sh`, or
regenerate it and add a CI drift check. Leaving a half-maintained second
lockfile is the worst of the three options.

### 5. `/inline-reply`'s 413 response is unreachable — oversized bodies get a connection reset

`electron/server/server.ts:139-150`

```ts
req.on('data', (c: Buffer) => {
  if (Buffer.concat(chunks).length + c.length > 16 * 1024) {
    tooLarge = true
    req.destroy()   // ← prevents 'end' from ever firing
    return
  }
  chunks.push(c)
})
req.on('end', () => {
  if (tooLarge) { res.writeHead(413, ...) }   // ← dead code
```

`req.destroy()` means `'end'` never fires, so the 413 is never written and the
client sees a reset instead of a status code.

**Verified** by driving `createServer` with a 20 KiB body over a real socket:
the client observes `ECONNRESET`, never `413`.

Secondary: the size check calls `Buffer.concat(chunks)` on every chunk, making
the guard O(n²) in chunk count. Track a running `total` integer instead, and
send the 413 before destroying (or simply stop accumulating and let `'end'`
arrive).

### 6. No Content-Security-Policy on the served SPA

Neither `index.html` nor the static-file handler in `electron/server/server.ts`
emits a CSP header or meta tag. The daemon serves this SPA to real browsers over
Tailscale / a reverse proxy, and the app renders agent transcript markdown
through `{@html renderMarkdown(...)}` (`src/lib/components/ChatView.svelte:468,505`).

`src/lib/markdown.ts` is a correct DOMPurify gate — sanitize plus an
`afterSanitizeAttributes` hook forcing `target=_blank` and
`rel="noopener noreferrer"` — so this is defense-in-depth, not an open hole. But
transcript content is attacker-influenced (it is whatever the agent read), and a
CSP is the cheap second layer if DOMPurify is ever bypassed or misconfigured.

Path traversal on that same handler is correctly guarded (decode, then
`startsWith(distDir + path.sep)`).

## Clean bills of health

Checked and found sound — recorded so the next audit can skip them:

- **No SQL injection surface.** Zero interpolated SQL; `electron/db/migrations.ts`
  uses static DDL strings only.
- **No shell injection surface.** Every child process uses `execFile`/`spawn`
  with an argv array; no `shell: true` anywhere.
- **`{@html}` usage is safe.** All non-markdown sites render static icon SVGs
  from `src/lib/icons.ts`; the only dynamic site goes through DOMPurify.
- **Secrets at rest.** Consistent `0o600` on key/salt files and `0o700` on data
  dirs (`configStore.ts`, `daemonManager.ts`, `services.ts`, `clipboardStore.ts`),
  with chmod-after-write covering the umask gap on refresh.
- **No secret logging.** No token/secret/password value reaches `console.*`.
- **Auth.** `resolveIdentity` compares via `timingSafeEqual` over SHA-256 digests,
  so token length does not leak. Bad ticket and bad token close identically
  (`4001`), leaking nothing.
- **Identity seam.** Aside from finding 2, every enumeration is
  `.filter(ownedByCaller)` and every by-id read goes through `ownedSession` /
  `requireOwnedRepo`, both of which collapse missing and not-owned into one
  response.
- **Branch-name injection.** `requireSafeBranch` rejects non-slug branches before
  they reach worktree paths (FLO-129).
- **No TODO/FIXME/HACK debt** in `electron/` or `src/`.
