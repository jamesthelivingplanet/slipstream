# Codebase audit — 2026-07-30 (v0.10.0)

A read-only sweep of the repo at `fcf02b9` (Release v0.10.0), split into the three
questions it was asked to answer: what existing features need **refining**, what features
we should **consider** building, and what **code quality** work is worth doing.

**Baseline at audit time.** `pnpm check` — 0 errors, 6 warnings. `pnpm lint` — clean
(eslint + prettier). `pnpm test` — **2827 tests across 126 files, all passing**, in 9.5s.
Nothing here is a fire. The backend is properly seamed (`electron/core/rpc.ts` is 150 lines
dispatching to 12 handler modules), services never cross-import, and the existing docs are
unusually candid about their own residual gaps. The findings below are about **drift**
(claims that stopped matching the code) and **unbounded edges** (paths with no ceiling),
not rot.

## 1. Features to refine

### A. Agent-initiated spawning has no fan-out or depth ceiling

The highest-value item in this audit.

`slipstream new-agent` shipped in 0.10.0. A spawned agent is launched with
`buildSystemPrompt` (`electron/services/agentSpawnService.ts:285`), and that prompt — at
`electron/shared/promptComposer.ts:65` — actively encourages delegation. So **every
spawned agent can itself spawn more**, with no limiting mechanism anywhere in the path:

- `agentSpawnService.ts` has no depth check, no per-parent child cap, and no rate limit.
  `parentId` is recorded (`:297`) and read exactly once (`:228`), purely to answer
  `slipstream agents`.
- `DEFAULT_SCHEDULER_POLICY = { maxConcurrent: 0 }` (`electron/shared/contract.ts:63`) —
  unlimited by default, so the queue is not a backstop either.
- `GcPolicy` (`contract.ts:43-56`) has no cost dimension; the reaper is idle/age/abandoned
  only.
- `getUsageSummary()` already computes real per-day spend. Nothing consumes it as a ceiling.

Net: one misbehaving or over-enthusiastic agent can fan out real PTYs and real API cost
without bound, and the only thing that stops it is a human noticing.

**Direction.** A `SpawnPolicy` alongside the existing two policies (`maxDepth`,
`maxChildrenPerSession`, `maxSpawnsPerHour`), enforced in `agentSpawnService.ts` before
`scheduler.submit`, surfaced under Settings → Behavior, and refused with a readable reason
on the requesting session's `responses.ndjson` so the agent learns why. Mirror
`SchedulerPolicy` exactly — it is the established precedent for a policy of this shape.

### B. "Blank chat" mode is launch-time-only and is lost on handoff

`mode: 'chat'` (`contract.ts:979`) is consumed once, at `electron/core/rpcHandlers/sessions.ts:73`
(pick the chat system prompt) and `:92` (`skipTicket`), and is **never persisted on the
session row**. Nothing downstream can tell a chat session from a ticket session except the
synthetic `CHAT-XXXXX` tid prefix minted client-side in `src/lib/stores.ts:722`.

The concrete break: `handoffSession` (`sessions.ts:297`) composes `buildHandoffPrompt` for
every session unconditionally — so handing a chat session to another agent hands it a
*ticket* takeover prompt, complete with the synthetic tid, the base branch, and the
open-a-merge-request framing that `buildChatSystemPrompt` deliberately strips out.

**Direction.** Persist `mode` on `SessionDTO` (additive migration), thread it through
`sessionLauncher`/`sessionStore`, add a chat-flavored handoff prompt, and map the field in
`dtoToSession` — see item L, which is the reason a missed mapping here would go unnoticed
until a reload.

### C. Kilo chat reads opencode's database

`electron/services/sessionChatReader.ts:124` routes kilo through the `usesEmbeddedServer`
branch, whose durable fallback is `deps.opencodeDbPath ?? opencodeDbPath()` (`:142`) —
hardcoded to `<XDG_DATA_HOME|~/.local/share>/opencode/opencode.db`. Kilo's own store is
`kilo.db`. So a kilo session's `opencodeSid` is looked up in the **wrong database**,
matches nothing, and the reader reports `available: false` — while
`electron/shared/agents.ts:66` claims `supportsChat: true`.

This is the verify-or-demote row that `docs/UX-GO-NO-GO.md` §1 flags as a B2 blocker.
It is now verified: **broken**, so it is fix-or-demote, not verify.

**It is a fix.** Inspected on this machine, `~/.local/share/kilo/kilo.db` is
schema-identical to `opencode.db` — same `message(id, session_id, time_created,
time_updated, data)` and `part(id, message_id, session_id, time_created, time_updated,
data)` tables, as expected of an opencode fork. So the fix is to parameterize the db path
by backend kind and reuse `readOpencodeMessagesFromStore` unchanged, exactly the way
`agentBackend.ts`'s `embeddedServerStatusTracking` factory is already shared between the
two backends.

> **Caveat worth carrying forward.** The kilo tables on this machine are *empty* (kilo was
> installed but never ran a recorded session), so the JSON shape of the `data` column is
> unverified against real kilo output. The reader's existing best-effort contract — never
> throws, skips malformed rows individually — means the worst case is an honest empty state
> rather than a crash, and it is strictly better than today's "read the wrong database".
> Confirm against a real kilo session before treating B2 as signed off.

### D. Backend capability claims are uneven and unverified

Three separate places assert what each backend can do, and they disagree:

| Backend | Chat | Usage/cost | Skills |
|---|---|---|---|
| claude-code | yes | yes (`transcripts`) | yes |
| opencode | yes | yes (`opencodeUsage`) | yes |
| pi | yes | yes (`piUsage`) | yes |
| grok | yes (`grokStore`) | **no** → `emptyUsage` | no |
| kilo | claimed yes, actually broken (item C) | **no** → `emptyUsage` | no |
| antigravity | no | **no** → `emptyUsage` | no |

`usage.ts:255` falls through to `emptyUsage` for the bottom three, so Mission Control's
cost signal **silently under-reports** for those sessions — and any cost ceiling built for
item A or E would inherit the same blind spot. Meanwhile `contract.ts:1127` and `:1150`
still name grok among the backends with no chat reader, which stopped being true when
`grokChatMessages.ts` landed.

**Direction.** Extend `AgentMeta` in `electron/shared/agents.ts` into a real capability
matrix (`supportsChat` / `supportsUsage` / `supportsSkills`), make the three consumers read
from it instead of restating it, and have the UI render the gaps honestly rather than
showing a zero that looks like "this session cost nothing".

## 2. Features to consider

**E. Cost budgets as a first-class policy.** The data already exists (`getUsageSummary`,
with a per-day rollup); the reaper only knows idle/age/abandoned. A per-day or per-session
spend ceiling that feeds both the reaper and item A's spawn gate is a small change with a
large safety payoff — especially now that agents spawn agents.

**F. Self-service device onboarding.** Rung 4 of `docs/PRODUCTION-READINESS.md` §1 is
gated mostly on this: `pnpm tokens -- issue` and hand the string over is the only path
today. A QR or pairing flow initiated from an already-authenticated session would move the
posture ladder further than any other single feature.

**G. Per-owner integration config.** The `config` table is deployment-global, and it is
named as a blocker for rung 5 and a caveat on rung 4. Every other part of the identity
seam is already `ownerId`-scoped — this is the odd one out.

**H. GitHub / GitLab Issues ticket providers.** `TicketSource` is `'jira' | 'linear'`
(`contract.ts:16`). Both would slot in behind `ITicketProvider` with no seam change, and
the git-provider half of the app already speaks GitHub, GitLab, Gitea and Bitbucket.

**I. Android reply token → Keystore.** `ReplyPrefs.java` keeps the daemon bearer token in
plaintext `MODE_PRIVATE` SharedPreferences, with a source comment calling Keystore-backing
a follow-up. `docs/UX-GO-NO-GO.md` B6 says explicitly that a source comment is *not* an
acceptable mitigation if the cut claims the Android shell — it needs Keystore-backing or a
written accepted-risk entry in `docs/SECURITY.md`.

## 3. Code quality

**J. Contract doc drift — four stale claims.** These matter more than ordinary comment rot
because `electron/shared/contract.ts` is the seam every implementation is written against:

- `:975` — `mode?: 'chat'` says "TASK-CIOEQ phase 3, **not yet wired**". It shipped in 0.10.0.
- `:1046` — "Phase-1 Bitbucket/Gitea **stubs** … reject until Phase 2". Both are fully
  implemented; `gitea.ts` and `bitbucket.ts` each do real PR creation and status fetching.
- `:1127` — says grok and kilo have no chat reader. grok has had one since `grokChatMessages.ts`.
- `:1150` — the same stale trio, for skills.

**K. Untyped RPC option.** `electron/core/rpcHandlers/chat.ts:274-277` reads
`includeSidechains` off `args[1]`, self-documented as "not the typed
`SlipstreamApi.getChatMessages` signature … out of scope this round". A handler option
living outside the contract is exactly the drift the contract exists to prevent — promote
it or drop it.

**L. `dtoToSession` silent-drop has no guard.** `src/lib/stores.ts:79`, with a comment at
`:108` warning that any unmapped field vanishes and that the gap only shows up after a
reload or reconnect. There is no test asserting every `SessionDTO` key is handled. A single
exhaustiveness test (or a `Record<keyof SessionDTO, …>`-shaped mapping) turns a whole class
of reload-only bugs into a compile error.

**M. Two god modules on the frontend.** `src/lib/stores.ts` is 1111 lines with 30+
writables spanning repos, ticket paging, session lifecycle, drafts and subscriptions —
while `src/lib/stores/` already holds five focused stores, so the split pattern exists and
simply has not been applied to the main file. `TerminalView.svelte` (1710) and
`MissionControl.svelte` (1524) are the other two.

> Both components sit inside the `docs/UX-GO-NO-GO.md` §3 freeze scope. This is a
> post-tag refactor, not a now one.

**N. Chat-mapper duplication.** `transcriptMessages.ts`, `piChatMessages.ts` and
`grokChatMessages.ts` each independently implement `blockFromRaw` / `imageBlockFrom*` /
`toolResultContentToParts` / `blocksFromContent` with near-identical shapes. A shared
block-normalizing core with per-backend adapters would cut roughly 200 lines and make a
rendering fix land once instead of three times. (`antigravityChatMessages.ts` is genuinely
different — it walks protobuf — and should be left alone.)

**O. Papercuts.** Six svelte-check warnings, all unused CSS in `NewAgentFab.svelte`
(`.new-agent-fab.pressed` and friends) — dead selectors left by a removed press state. And
a fresh linked worktree's `mise.toml` is untrusted, so `pnpm check`/`test`/`lint` fail with
a mise error instead of running; worth either a note in `docs/DEVELOPMENT.md` or a
`mise trust` in the worktree scaffold.

### What landed next, same day

E, F, G and H in full; I implemented but not field-verified. Gate after:
`pnpm check` 0 errors (6 pre-existing warnings, item O), `pnpm lint` clean, `pnpm test`
**3014 passing** — up from 2827 at audit time, so +187 tests across the whole effort.

Three things are deliberately *not* claimed as fully closed, and each is written down in
the relevant doc rather than left to be rediscovered:

- **I is compile-verified, not field-verified.** The Android change builds
  (`gradlew assembleDebug`, BUILD SUCCESSFUL) but four runtime behaviors need a real device:
  `AndroidKeyStore`/`MasterKey` initialization, the plaintext→encrypted migration against a
  real prior install, `ReplyReceiver` decrypting and POSTing with the app process dead, and
  the degrade path when Keystore init fails. `docs/UX-GO-NO-GO.md`'s B6 row should be read
  as "mitigation implemented, not field-verified" until someone runs it on hardware.
- **G leaves two known gaps**, recorded in `docs/IDENTITY-SEAM.md`: git-push credential
  reads in `prStatus.ts`/`gitDriver.ts`/`slipstream.ts` still use the deployment-global
  path, and per-owner data directories (item 5) remain open. What *is* closed is the gap the
  readiness doc actually names — ticket and git-host credentials are now genuinely
  owner-scoped, with providers resolved per request rather than as startup singletons.
- **C's kilo caveat is unchanged.** Still schema-verified only.

G is worth a note on how it got there: the first pass delivered git-host isolation but left
ticket providers scoped only *structurally* — they read owner-scoped keys while being
constructed once at startup, so no per-request identity ever reached them, and Linear was
untouched entirely because `linear.apiKey` had a second writer. That is a failure mode worth
naming: the change looked complete and tested green while the headline gap stayed open. It
took a follow-up pass to make the scoping actual.

## Suggested ordering

A → C → J → B. The first two are the only items that are actively unsafe or actively wrong
today; J is cheap and stops the seam lying to the next reader; B is a correctness gap that
only bites on a path (handoff of a chat session) that is not yet common.
